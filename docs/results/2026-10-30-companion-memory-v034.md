# Companion内存检查与v0.3.4补丁

基线05c28b2。用户报告本机确认配对后，手机发起连接时出现“内存资源不足，无法处理此命令”。

## 系统证据

- Windows系统日志在2026-10-30 13:45:09、13:47:09、13:52:28记录事件2004，明确报告虚拟内存不足。此处应观察系统提交量/上限，不能仅看物理内存工作集。[微软排查说明](https://learn.microsoft.com/en-us/troubleshoot/windows-server/performance/troubleshoot-application-service-memory-leaks)
- 13:52:47，Companion 0.3.3在tk86t.dll中以c0000005崩溃；与最近一次资源不足相隔19秒。更早版本已有tcl86t.dll/80000003事件，因此只能将内存压力视为本次崩溃的重要伴随因素，尚未证明原生崩溃的唯一原因。
- 检查时16GiB机器的可用物理内存一度仅552MiB，提交占比89%。任务遗留的Gradle/Kotlin进程合计约2.8GiB私有提交，模拟器在一次资源事件中约4GiB，用户高内存应用在后续事件中约7.5GiB。测试负载与日常负载共同增加压力。
- 通过正常Gradle停止回收任务构建进程，按路径、命令和创建时间校验后回收本任务遗留的两层测试进程，确认已退出。未终止用户应用、未修改分页文件、注册表、全局配置或安全设置。后续系统恢复约4.5GiB可用物理内存、约6.9GiB提交余量后，仅构建Windows补丁，没有再启动Android构建或模拟器。
- USER/GDI资源检查没有发现明显的每进程配额耗尽证据。未据此调整桌面堆。

## 连接重试的独立结果

资源压力下降后，用户手机仍显示“连接暂时不可用，请检查电脑在线状态。待核对操作不会重发”。确认手机为Android 0.3.3；本机Companion 0.3.3进程仍运行，界面显示中继已接受连接，配置与配对记录保留，未发现此次重试的新崩溃。因此内存回收尚未解决当前连接失败，需要接入阶段证据。

授权55条目录本身不启动运行时子进程；用户进入单条历史时才使用短时读取进程。未发现连接时批量启动55个读取进程的逻辑，也未逐条读取用户原会话来验证此判断。

## 改动

- 服务关闭线程仅捕获Host，避免持有整个Tk窗口；GUI在工作线程实际退出后才销毁窗口。关闭异常仅保存文本，不把带有线程帧的异常对象传回GUI。
- 关闭时取消待执行刷新回调。最初五轮隐藏窗口重开实际复现了`invalid command name ...refresh`；修正后同样探针无标准错误输出。没有扩展为未经证明的单Tk根窗口重构。
- 新增仅在本机内存保留3条的固定阶段诊断和通道到达计数。事件不接收任意错误文本、消息或标识，不修改协议、授权或恢复记录；不新增远程管理接口。写出回复不等同于手机接收确认。
- 仅更新Companion至0.3.4，Android保持0.3.3，线上Worker不变。新便携目录继续引用原有完整配置，保留身份、授权、策略与日志。

## 验证与限制

- 25项检查通过：离线启动/配置14，关闭生命周期3，安全状态显示6，嵌套TLS配对与认证读取1，匿名/未登记设备拒绝1。
- 五轮真实Tk隐藏窗口关闭/配置重开运行于有15秒超时的独立进程，无旧回调错误，结束后没有存活工作线程。关闭线程延迟退出与关闭异常均有独立检查。
- TLS验证仅使用项目自有回环中继、合成身份和消息。没有向原Codex/ChatGPT会话发消息、没有扩大授权、没有改公网中继。
- 原生c0000005崩溃未在本轮重现；本次真实手机连接失败也尚未核实解决。补丁的接入阶段显示用于下一次真实重试定位，不能将上述离线通过等同于公网连接已通过。
